# 文件合并异步任务技术选型

## 背景

当前分片上传在全部分片到达后，由前端调用合并接口。接口同步读取分片、校验完整文件，并登记网盘文件。大文件合并耗时较长，会占用 HTTP 请求和后端工作线程。目标是让接口快速返回，同时可靠地把合并任务交给后台执行，并能查询状态、处理重试和服务重启。

## 选型结论

当前采用 **MySQL 任务表 + 有界 Spring `TaskExecutor` 线程池**。

MySQL 保存持久化任务状态和结果，线程池负责实际文件合并。该方案复用现有 Spring Boot 与 MySQL，无需新增消息中间件，适合当前单台服务器、单个后端容器的规模。异步化不减少文件的磁盘占用，也不减少合并所需的磁盘读写。

## 方案对比

| 方案 | 优点 | 成本或不足 | 当前结论 |
| --- | --- | --- | --- |
| MySQL 任务表 + 有界 Spring 线程池 | 复用现有组件；任务状态持久化且可查询；线程池并发和队列容量可控；部署简单 | 需要自行实现原子领取、失败重试和重启恢复 | **当前采用** |
| Redisson 延迟队列 | 可延迟投递；若已有 Redisson，接入方便 | 延迟投递不等于完整任务可靠性；确认、失败重领、恢复和业务状态仍需设计；本任务通常无需延迟 | 暂不采用 |
| Redis Streams | 消费者组分摊任务；有确认和待处理记录，可接管长期未确认消息 | 需要维护消费组、确认、重试、待处理消息恢复；任务业务状态仍建议存 MySQL | 有多个消费者需求时再评估 |
| RabbitMQ | 消息确认、重试和死信等机制成熟；适合跨进程和多服务消费 | 新增部署、监控和运维组件；当前规模引入成本较高 | 拆分 worker 或扩大规模后再评估 |
| 仅使用内存线程池 | 实现最简单 | 进程重启会丢失排队任务；没有持久化状态和恢复依据 | 不单独用于生产任务管理 |

## 处理流程

1. 前端提交合并请求，后端验证登录用户、上传会话归属、分片完整性和会话状态。
2. 后端在 MySQL 创建 `PENDING` 任务并返回 `202 Accepted` 与任务编号。重复提交同一上传会话时返回已有任务，避免生成重复任务。
3. 后台线程原子领取任务，将状态改为 `PROCESSING`，按序流式合并分片并校验总长度和 MD5。
4. 合并成功后登记物理文件和用户文件记录，任务变为 `SUCCESS`，保存可供前端读取的文件 ID。失败时保存 `FAILED` 状态和可诊断的错误摘要。
5. 前端通过任务状态接口轮询；遇到成功或最终失败后停止轮询。文件记录只允许成功任务创建，重复执行必须幂等。
6. 应用启动后扫描遗留任务：重新投递 `PENDING` 任务；对超过处理租约且仍为 `PROCESSING` 的任务，按恢复策略重新排队或标记待人工处理。

## 可靠性与资源约束

- **持久化**：任务状态保存在 MySQL，不以 JVM 内存队列作为唯一事实来源。
- **并发限制**：配置有界线程池，明确核心线程数、最大线程数、队列容量和拒绝策略。初期可从 1 个合并线程开始，根据服务器磁盘、CPU 和内存监测结果调整，避免多个大文件并发合并挤满资源。
- **原子领取**：使用数据库条件更新或行锁保证同一任务只被一个 worker 同时领取；设置处理租约，允许崩溃任务恢复。
- **幂等性**：以上传会话/任务作为幂等键；合并产物发布和数据库登记需要处理重试及崩溃边界，避免重复文件记录或遗留临时文件。
- **事务边界**：不要在持有长时间数据库事务或行锁时进行大文件 I/O。短事务负责领取、状态更新和最终登记；合并过程使用临时文件，校验成功后再原子发布。
- **失败处理**：区分可重试的瞬时错误和不可重试的完整性错误；限制重试次数并记录失败原因。保留分片以便重试，成功后再清理。
- **状态接口权限**：查询任务时校验任务所属用户，不能仅凭任务 ID 泄露其他用户的文件状态或结果。
- **容量治理**：为任务记录定义保留与归档策略；监控待处理数、失败数、处理时长、重试次数和磁盘空间。

## 接口形态建议

- `POST /api/v1/files/file/chunk-upload/complete?uploadId=...`：提交合并任务，任务已接收时返回 `202 Accepted`、`taskId` 和初始状态。
- `GET /api/v1/files/file/chunk-upload/tasks/{taskId}`：返回当前用户任务状态；成功时包含文件记录，处理中时可包含阶段或进度。

任务状态建议为 `PENDING`、`PROCESSING`、`SUCCESS`、`FAILED`。任务表至少记录任务 ID、上传会话 ID、用户 ID、状态、尝试次数、创建/开始/完成时间、租约时间、结果文件 ID和错误摘要。上传会话和任务需要通过唯一约束或等效并发控制保证一对一提交语义。

## 后续扩展条件

当后端扩展为多个实例、需要 API 与合并 worker 独立部署、任务持续积压，或需要成熟的跨服务投递与死信运维能力时，再评估 **MySQL 业务任务表 + RabbitMQ**。若已有可靠运营的 Redis Streams 集群和相应监控，也可评估 Streams 消费者组。无论引入哪种消息队列，MySQL 仍保存用户可见的业务任务状态，消息只负责唤醒/分发 worker，并通过幂等和确认机制处理重复投递。
