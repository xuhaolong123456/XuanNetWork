## 一、测试驱动开发：单元测试&回归测试
1. **针对创建文件夹做测试用例设计**
需要补充单元测试+回归测试，覆盖边界场景：空名称、名称超长、非法特殊字符、父目录不存在、越权访问、父节点本身是文件、同名文件夹自动编号等。
不是靠手动点页面验证功能，而是用测试用例保证正确性。
2. **回归测试价值**：锁定已有业务行为，修改代码之后，运行测试就能快速发现代码改动破坏原有逻辑。
3. **构建踩坑**：`mvn test`抛出`NoClassDefFoundError`，不一定是第三方库（springdoc）问题，大概率是target目录残留旧的半编译class文件；执行`mvn clean test`清理后再测试即可。

## 三、错误码与全局异常设计
1. 现有方案：使用裸字符串常量表示业务错误码，自定义两类业务异常：认证异常`AuthException`、文件业务异常`FileBusinessException`；通过`GlobalExceptionHandler`全局异常拦截器，把业务异常映射成对应的HTTP状态码返回前端。
2. 当前存在的设计缺陷
    - 同一个业务含义错误码映射多个HTTP状态码：例如`FILE_TOO_LARGE`同时出现400、413；
    - `FILE_NOT_FOUND`语义过载，复用在多种不同的业务场景；
    - 使用裸字符串常量，没有使用枚举做约束，容易写错字符串。
3. 收获：开发要清晰认知自己方案的设计边界、现存缺陷。

## 四、存储架构：文件元数据与文件内容分离
> 网盘核心架构思想，不要把文件二进制存入数据库BLOB字段
1. MySQL数据库只保存**元数据**：文件名、大小、MIME类型、`storageKey`存储指针、文件父子树形关系、归属用户等描述信息。
2. 文件真实二进制字节存储在本地磁盘路径 `./uploads/{ownerId}/{uuid}`。
3. 为什么不把文件字节存入数据库BLOB：会造成数据表急剧膨胀，数据库查询性能严重下降。
4. `storageKey`作为桥梁，把数据库元数据记录，和磁盘真实文件关联起来。

## 五、递归删除技术选型（文件夹删除核心决策）
针对文件夹删除，5个关键决策点，每一项都要思考选型理由、权衡利弊：

|决策维度|MVP选型|选型理由|
|---|---|---|
|软删除 vs 物理删除|物理删除起步，软删除作为后续迭代|软删除改动面大，影响查询、同名校验、后台清理逻辑；MVP阶段太重|
|级联删除放在哪一层|应用业务层递归|数据库外键`CASCADE`只能删数据库记录，无法操作磁盘文件，满足不了业务|
|递归查询实现|BFS广度优先；复杂场景可以用CTE|BFS代码简单、便于单元测试；CTE单条SQL，但要注意防环|
|并发控制|悲观锁|删除属于短事务、强一致性场景，使用悲观锁保障并发安全|
|磁盘删除执行时机|事务提交afterCommit之后再执行磁盘删除|数据库事务可以回滚；如果磁盘操作失败，数据库可以回滚，保证一致性|

> 关键点：数据库事务只能保护数据库操作，**磁盘IO操作无法被事务回滚**。

## 六、软删除完整正确设计（回收站业务）
1. **字段选型优先使用`deleted_at`时间戳，而不是单纯布尔值`is_delete`**
布尔只能标记删/未删；时间戳可以记录删除发生的时刻，用于回收站过期倒计时、后台定时清理过期回收站数据。
2. **软删除带来经典坑：同名冲突**
回收站里面存在同名文件夹/文件，不能阻挡用户新建同名资源；新建、重命名做同名校验的时候，**只统计`deleted_at IS NULL`未删除的数据，要过滤掉已经软删除的数据**。
3. **恢复功能也要处理同名冲突**
把回收站项目恢复到目标目录，如果目标目录已经存在同名文件/文件夹，需要复复用`handleDuplicateFilename`逻辑，自动重命名，避免名字冲突报错。

## 七、REST API硬规范
1. 分清概念：`UPDATE`是SQL数据库语句，**不是HTTP方法**；HTTP标准方法只有：`GET POST PUT PATCH DELETE`。
2. 单条删除：`DELETE /api/v1/files/{id}`，**使用id定位资源，不要使用name，会出现重名歧义**。
3. 批量删除：不建议`DELETE`请求携带body（HTTP语义存在争议），推荐`POST .../batch‑delete`自定义批量接口。
4. 返回码细节：单删成功返回`204 No Content`没有响应体；**批量删除不能直接全部返回204，如果出现部分成功、部分失败，要返回200，在响应体返回失败条目清单**。

## 八、业务需求：单删、批量逻辑删除（仅操作元数据，不碰磁盘）
> 迭代需求：逻辑删除，支持回收站恢复，不操作磁盘真实文件
### 单删除
1. 后端校验该资源属于当前登录用户；
2. 文件：自身打上软删除标记；文件夹递归整棵子树全部打上软删除标记；
3. 前端：行删除按钮、二次确认弹窗、toast提示。

### 批量删除
1. 入参ids数组；全部资源校验归属当前登录用户；只要任意一条没有权限，整体拒绝，数据库不做任何改动；
2. 如果选中包含文件夹，递归标记全部子节点；
3. 前端列表复选框，勾选之后展示批量删除按钮，二次确认弹窗。

### 查询规则
1. 普通文件列表：过滤已删除记录；
2. 回收站页面：查询被软删除的数据；
3. 恢复接口：恢复标记；处理恢复时同名冲突。

### HTTP方法区分
- `PUT`：全量替换整个资源；
- `PATCH`：局部更新部分字段；软删除只修改少量字段，语义上优先PATCH；
- `UPDATE`：SQL语句，后端ORM执行的数据库操作。

### 数据库视图View
1. 视图是虚拟表，不存储真实数据，只是保存一条SELECT语句；查询视图时动态计算返回视图记录。
2. 用途：封装查询条件，自动过滤软删除；
3. 局限：SQLite视图仅支持读，不支持update/delete写入；
4. 项目建议：不使用数据库视图，优先Repository层封装查询函数实现相同能力。

## 九、ORM、JPA、Hibernate、TypeORM概念体系
1. **ORM 对象关系映射**：程序对象 ↔ 关系数据库表互相映射，开发操作对象，框架自动生成SQL。两种模式：
    - ActiveRecord：对象实例自带save/delete方法；
    - DataMapper：实体只是普通对象，由外部Repository/EntityManager中介完成持久化。
2. **JPA**：Java平台的ORM**规范（接口、注解标准），本身不是可运行框架**。依靠EntityManager做实体快照对比；持久态对象修改属性，事务提交自动生成SQL；游离状态对象修改属性不会自动更新。
3. **Hibernate**：ORM框架，**实现JPA这套规范**。
4. **Spring‑Data‑JPA**：Spring封装，简化JPA开发。
5. **TypeORM(NestJS/TS)**：ORM框架，借鉴JPA思想，**不属于JPA**；修改对象属性后必须显式调用`save/update`，没有自动脏检查。

> 层级关系：ORM（思想概念） → JPA（Java的ORM接口规范） → Hibernate（实现规范的ORM框架） → Spring‑Data‑JPA（上层封装）

### 高频坑总结
1. JPA存在N+1查询；`@Where`全局过滤注解会干扰回收站查询；
2. 软删除只是标记，必须有后台物理清理，否则数据库无限膨胀；
3. PUT作用集合资源语义是整体替换，不适合批量局部更新；
4. 数据库事务无法保护磁盘IO。

## 十、Web安全知识点
1. 请求对象DTO：后端使用专门的`XXXRequest`Java接收类映射前端JSON请求体；字段、校验规则全部定义在请求对象中。
2. CSRF安全问题：
    - 现象：toast提示请求校验失败，请求还没走到业务逻辑就被安全层拦截；
    - 原因：`X‑XSRF‑TOKEN`请求头令牌与Cookie中的令牌不一致；
    - 本项目登录身份存储在HttpOnly Cookie；浏览器请求必须同时携带对应Cookie和CSRF请求头。
