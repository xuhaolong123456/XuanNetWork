# JUnit 与 JMeter 测试区别

## 1. 核心区别

JUnit 和 JMeter 都可以测试 Java 项目，但目标不同：

| 工具 | 主要目标 | 关注内容 |
|---|---|---|
| JUnit | 验证代码和业务逻辑是否正确 | 结果是否正确、异常是否符合预期 |
| JMeter | 验证接口在压力下是否稳定 | QPS、响应时间、并发能力、错误率 |

简单来说：

```text
JUnit 关注“功能对不对”
JMeter 关注“压力下能不能稳定运行”
```

## 2. JUnit 的测试范围

JUnit 通常运行在代码层或应用内部，适合测试：

- 验证码是否为 6 位数字
- 验证码是否正确校验
- 验证码是否过期
- 验证码是否只能使用一次
- 60 秒内重复发送是否被拒绝
- 注册参数是否合法
- 邮箱或昵称重复时是否返回错误
- 密码是否被 BCrypt 加密
- Controller 是否正确调用 Service
- 异常是否符合预期

JUnit 的特点：

- 测试执行速度快
- 结果稳定、容易定位问题
- 可以使用 Mock 隔离邮件、数据库等外部依赖
- 适合每次提交代码后自动执行
- 通常不需要真实发送邮件

JUnit 主要回答：

> 这段代码在给定输入下，业务结果是否正确？

## 3. JMeter 的测试范围

JMeter 通常通过 HTTP 调用已经启动的后端服务，适合测试：

- 多用户同时请求发送验证码
- 接口在高并发下的响应时间
- 接口每秒能处理多少请求
- 并发增加后错误率是否上升
- Tomcat 线程池是否耗尽
- 数据库连接池是否不足
- JVM CPU、内存和线程使用情况
- 系统是否出现超时、拒绝连接或 5xx 错误

JMeter 的特点：

- 面向真实 HTTP 接口
- 可以模拟多个并发用户
- 能统计 QPS、平均响应时间、P90/P95/P99 和错误率
- 适合生成性能测试报告
- 运行时间长、资源消耗大
- 结果会受到机器、网络、数据库和外部服务影响

JMeter 主要回答：

> 这个接口在一定并发压力下，能否保持可接受的性能和稳定性？

## 4. 为什么两者测试范围不同

两者处于不同测试层级：

```text
JUnit
  ↓
代码逻辑、Service、Controller、参数校验

JMeter
  ↓
HTTP 接口、Tomcat、线程池、数据库、整体运行环境
```

JUnit 可以直接调用 Java 方法，例如：

```java
service.verify(email, code);
```

JMeter 则调用真实接口：

```http
POST /api/v1/auth/email-code
```

因此，JUnit 更容易精确定位代码问题；JMeter 更接近用户真实访问系统的情况。

## 5. 本项目中的分工

### JUnit 测试

当前项目使用 JUnit 覆盖：

- `EmailCodeServiceTest`
- `AuthControllerRegressionTest`
- `EmailRegisterFlowRegressionTest`
- `AuthServiceTest`
- `RegisterRequestValidationTest`

这些测试验证验证码和注册业务是否正确，使用 Mock 邮件发送器，不会发送真实邮件。

### JMeter 测试

当前项目使用 JMeter 压测：

- `POST /api/v1/auth/email-code`
- 并发请求能力
- 响应时间
- QPS
- 错误率
- P90/P95/P99 延迟

压测时必须设置：

```powershell
$env:MAIL_ENABLED="false"
```

这样可以保留验证码业务逻辑，但不会连接 QQ SMTP 或发送真实邮件。

## 6. 两者不能互相替代

只使用 JUnit，可能发现不了：

- 并发请求导致响应变慢
- 线程池耗尽
- 数据库连接池不足
- 内存持续增长
- 接口在高压力下返回 5xx

只使用 JMeter，可能发现不了：

- 某个边界条件判断错误
- 验证码没有一次性删除
- 重复邮箱判断错误
- 参数校验规则错误
- 异常分支没有正确处理

因此两者应该配合使用：

```text
先用 JUnit 验证功能正确
    ↓
再用 JMeter 验证性能和稳定性
```

## 7. 推荐执行顺序

日常开发：

```powershell
cd backend
mvn test
```

发布前性能验证：

1. 启动后端服务。
2. 设置 `MAIL_ENABLED=false`，防止发送真实邮件。
3. 使用 JMeter 非 GUI 模式执行测试计划。
4. 生成 HTML Dashboard 报告。
5. 查看 QPS、P95、错误率和服务器资源。
6. 根据结果调整线程池、数据库连接池或验证码存储方案。

## 8. 当前方案的测试边界

JUnit 和 JMeter 当前都没有验证真实 QQ 邮箱的发送性能，因为压测真实邮箱可能触发风控、发送大量邮件或消耗个人邮箱额度。

真实 SMTP 只适合做少量人工联调；性能测试应使用关闭邮件发送的业务模式，或者使用专用测试 SMTP 服务。

## 9. 性能测试核心指标

### 9.1 QPS

QPS 是 Queries Per Second 的缩写，表示系统每秒处理的请求数量。

例如：

```text
QPS = 500
```

表示系统平均每秒完成 500 个请求。

QPS 越高不一定越好。如果响应时间很高、错误率也很高，说明系统是在勉强处理请求。应该结合 P95 和错误率一起判断。

### 9.2 P95 响应时间

P95 表示 95% 的请求响应时间不超过这个数值，剩余 5% 的请求会更慢。

例如：

```text
P95 = 300 ms
```

表示 95% 的请求在 300 毫秒内完成，只有 5% 的请求超过 300 毫秒。

P95 比平均响应时间更能反映用户体验，因为平均值可能掩盖少量特别慢的请求。

### 9.3 错误率

错误率表示失败请求占总请求的比例：

```text
错误率 = 失败请求数 / 总请求数 × 100%
```

常见错误包括：

- HTTP 5xx
- 连接超时
- 连接被拒绝
- 数据库连接失败
- 业务异常

验证码接口中，因业务规则被限流的请求属于业务拒绝，需要和系统异常区分统计。

### 9.4 CPU 和内存

CPU 反映服务器处理请求时的计算压力，内存反映应用和 JVM 使用的内存数量。

常见判断方式：

- CPU 长时间接近 100%：可能是计算、加密、线程调度或日志处理成为瓶颈。
- 内存持续增长：可能存在缓存、验证码记录或对象未释放问题。
- 频繁 Full GC：说明堆内存压力较大或对象创建过多。
- CPU 不高但响应很慢：瓶颈可能在数据库、网络、锁或连接池。

### 9.5 Tomcat 线程数

Tomcat 使用工作线程处理 HTTP 请求。并发请求增加时，线程数会增加或进入等待队列。

如果线程池耗尽，可能出现：

- 请求排队
- P95/P99 响应时间明显上升
- 请求超时
- 新请求无法及时处理

Tomcat 线程数需要结合最大线程数、活跃线程数和请求队列一起观察。

### 9.6 数据库连接池

数据库连接池保存可复用的数据库连接，避免每次请求都重新建立连接。

如果连接池太小：

- 请求会等待数据库连接
- 响应时间增加
- P95 和 P99 上升

如果连接池太大：

- 数据库可能被大量连接压垮
- 消耗更多内存和数据库资源

需要观察活动连接数、空闲连接数、等待连接数和连接获取耗时。

## 10. 为什么当前测试可能测不到瓶颈

当前 JMeter 测试计划默认只有 20 个并发线程，压力较低，且验证码接口在 `MAIL_ENABLED=false` 时不会访问真实 SMTP，因此可能看不到明显瓶颈。

此外，验证码发送接口当前主要使用内存 Map 保存验证码，不一定会访问数据库，所以数据库连接池压力可能很小。真正注册接口才会涉及用户查询、密码 BCrypt 加密和数据库写入。

建议分阶段增加压力：

```text
100 并发 → 500 并发 → 1000 并发 → 5000 并发 → 10000 并发
```

每个阶段至少持续 1-5 分钟，并记录 QPS、P95、错误率、CPU、内存、Tomcat 线程和数据库连接池。不要一开始就直接使用 1 万并发，JMeter 客户端本身可能先成为瓶颈。
