# 公网访问时 `/me` 接口阻塞排查记录

记录日期：2026-10-04

## 用户反馈

访问 `http://110.42.218.20:5173/` 时页面组件没有正常加载，浏览器控制台出现资源 404 和请求 500。开发者工具网络面板显示多个 `me` 请求：一个请求最终返回 HTTP 500，耗时约 2.3 分钟；另外两个仍处于待处理状态。

## 已核实情况

- 从当前工作环境访问公网服务，`/`、`/@vite/client`、`/src/main.js`、`/src/style.css` 均返回 HTTP 200，说明检查时公网 5173 上的 Vite 开发服务器可提供页面入口及主要前端模块。
- 对 `/api/v1/auth/me`、`/api/v1/auth/csrf` 和图形验证码接口进行探测时，请求超时；这与浏览器看到的 `/me` 长时间等待相符。
- 前端原路由守卫会对每次导航请求 `/api/v1/auth/me`。根路径 `/` 又会重定向至 `/drive`，并发导航可能造成重复的会话检查。
- 后端 `/me` 使用 `@AuthenticationPrincipal` 获取用户编号。请求经过 `JwtAuthenticationFilter` 时，如果携带有效认证 Cookie，还会检查 Redis 中的令牌状态并读取数据库中的用户记录。因此后端依赖访问异常可能使认证链路失败或变慢。
- 目前没有取得部署服务器上与该 500 对应的后端异常堆栈，尚不能确认 Redis、数据库、反向代理或其他部署配置中的具体根因。此前公网探测中 API 表现为超时，浏览器截图中一个请求最终为 500；二者说明服务端处理不稳定，但不足以断定具体故障点。

## 已完成的前端调整

`frontend/src/main.js` 已调整路由守卫：

- 仅在需要身份判断的受保护页面或访客专用页面调用会话接口。
- 合并并发的会话检查，避免同时发出多个 `/me` 请求。
- 前端生产构建 `npm run build` 已通过。

此调整减少重复请求，但不会修复服务端 `/me` 返回 500 的根因。远端 5173 若运行的是旧进程或旧构建，仍需重新部署/重启前端后才能应用。

## 后续诊断

1. 复现一次问题并记录精确时间，在部署主机检查后端日志中同一时间的异常堆栈。
2. 检查后端进程是否正常监听 9090，以及从后端主机到 Redis、MySQL 的连接是否可用。
3. 检查远端 Vite `/api` 代理目标。当前 `frontend/vite.config.js` 将 `/api` 固定代理至 `http://localhost:9090`；只有前后端运行在同一主机且后端监听本机 9090 时才适用。
4. 更新前端后重新打开网络面板，确认重复 `/me` 请求已消失，并观察剩余请求的状态和耗时。

## 安全提示

排查时不要在日志、截图或共享记录中粘贴 JWT、Cookie、CSRF 令牌、邮箱验证码或数据库凭据。
