# 逻辑删除与回收站

## 接口

| 操作 | 方法与地址 | 请求体 | 成功 |
| --- | --- | --- | --- |
| 单删 | PUT `/api/v1/files/file/{id}` | 可空，按路径 ID 操作 | 204，无响应体 |
| 批量删除 | PUT `/api/v1/files/files` | `{"ids":[1,2]}` | 204，无响应体 |
| 单条恢复 | PUT `/api/v1/files/recover/{id}` | 空 | 204，无响应体 |
| 批量恢复 | PUT `/api/v1/files/recover/batch` | `{"ids":[1,2]}` | 204，无响应体 |
| 回收站列表 | GET `/api/v1/files/recycle-bin?page=0&size=50` | 无 | 200，现有 Result 包装 |

旧 DELETE `/api/v1/files/directories/{id}` 兼容入口也改为逻辑删除，成功返回 204。

认证复用项目现有 HttpOnly JWT Cookie；写请求继续携带 `X-XSRF-TOKEN`。项目原有安全规则明确忽略 Bearer Header，本次保持这一规则。前端复用 fetch，无需新增 axios。

删除与恢复失败返回 `{"code":400,"msg":"错误描述","data":null}`。参数错误 400、未登录 401、资源归属不符 403、不存在 404；目录结构异常可返回 409。

## 数据规则

- 删除只更新 `user_file`，不删除数据库记录，不调用存储服务，不操作磁盘。
- `is_delete=1`、`delete_at=当前时间`，同批次共享 `delete_batch`；恢复清除这三个标记。
- 普通目录列表、文件树和名称冲突查询只读未删除记录；回收站只读当前用户的已删除记录。
- 批量最多 1000 个 ID，去重后先全量校验归属和存在性，再更新。删除和恢复均在同一事务内执行，失败整体回滚。
- 按主键游标每次最多遍历、更新 200 个后代，使用队列避免深层递归栈溢出。事务提交前仍持有行锁；分批不等于消除大目录长事务成本。
- 同用户写操作先取得用户行锁，与创建、改名采用一致的加锁顺序，防止删除过程中创建子目录。

## 恢复边界

- 恢复目录会恢复本次删除批次的后代，更早单独删除的子树仍留在回收站。
- 单独恢复子项会补齐其祖先目录，但不会带回其他被删除的兄弟项。
- 原目录存在同名内容时复用 `handleDuplicateFilename()`，例如 `文件（1）.pdf`。
- 重复删除、重复恢复允许成功；重复删除不覆盖原删除批次或时间。
- 本次改造前已经物理删除的数据库记录无法恢复。

## 本地数据库升级

当前开发配置使用 JPA `ddl-auto=update`，重启后会补充新字段与索引。若改用手工管理表结构，先检查字段是否已存在，再执行同目录下的升级 SQL；不要对已由 JPA 升级的表重复执行。

## 验证

运行 `mvn test`、`node --test src/api/files.test.js` 与 `npm run build`。
数据库集成测试使用 H2，覆盖递归、越权、整批预校验、分批遍历、同名恢复和不调用存储服务。MySQL 实例的真实并发及大目录性能仍需单独验证。
