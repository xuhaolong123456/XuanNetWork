# 邮箱验证码模块说明

## 1. 模块职责

邮箱验证码模块用于注册时验证用户是否能够访问提交的邮箱地址。

后端负责：

- 生成 6 位数字验证码
- 通过 QQ SMTP 发送验证码
- 保存验证码及生成时间
- 校验验证码是否正确、过期或重复使用
- 限制验证码发送频率

前端只负责输入邮箱、调用发送接口和提交验证码，不能信任前端校验结果。

## 2. 调用流程

```text
用户输入邮箱
    ↓
点击“获取验证码”
    ↓
POST /api/v1/auth/email-code
    ↓
后端生成验证码并通过 QQ 邮箱发送
    ↓
用户填写验证码和其他注册信息
    ↓
POST /api/v1/auth/register
    ↓
后端校验邮箱验证码
    ↓
校验成功后创建用户
```

## 3. 接口说明

### 3.1 发送验证码

请求：

```http
POST /api/v1/auth/email-code
Content-Type: application/json
```

```json
{
  "email": "user@example.com"
}
```

成功后，验证码会发送到该邮箱。

### 3.2 注册

请求中的 `emailCode` 必须是发送到该邮箱的有效验证码：

```json
{
  "email": "user@example.com",
  "emailCode": "123456",
  "nickName": "user001",
  "password": "123456"
}
```

后端会先校验验证码，再执行用户注册和密码加密。

## 4. 配置方式

不要把 QQ 邮箱授权码写入源码。启动后端前配置环境变量：

```powershell
$env:MAIL_USERNAME="你的QQ邮箱"
$env:MAIL_PASSWORD="你的QQ邮箱授权码"
```

当前 SMTP 配置：

- SMTP 主机：`smtp.qq.com`
- SMTP 端口：`587`
- 认证方式：账号 + 授权码
- 加密方式：STARTTLS

## 5. 当前规则

- 验证码长度：6 位数字
- 有效期：5 分钟
- 重发间隔：60 秒
- 验证成功后立即删除
- 同一个验证码只能使用一次
- 邮箱地址会去除首尾空格并统一转换为小写
- 后端发送失败时不会保存验证码

## 6. 当前实现边界

验证码目前保存在后端单机内存中，因此：

- 后端重启后，已有验证码会失效
- 多实例部署时，各实例之间不会共享验证码
- 内存数据不适合长期保存或审计

生产环境建议将验证码和过期时间保存到 Redis，并进一步增加：

- 按 IP 限流
- 按邮箱限流
- 每日邮件发送上限
- 图形验证码或风控校验
- 邮件发送失败日志和监控

## 8. 前后端完整注册链路

### 8.1 前端发送验证码

注册页面调用 `getEmailCode()`：

1. 检查邮箱格式。
2. 调用 `sendEmailCode(email)`。
3. 请求后端 `POST /api/v1/auth/email-code`。
4. 请求成功后，前端显示 60 秒倒计时。

前端倒计时只用于用户体验，不能作为安全限制。真正的 60 秒发送限制由后端执行。

### 8.2 后端发送验证码

请求到达 `AuthController.sendEmailCode()` 后：

1. Spring 校验邮箱格式。
2. `EmailCodeService` 将邮箱去除首尾空格并转换为小写。
3. 检查该邮箱是否处于 60 秒重发限制期。
4. 使用 `SecureRandom` 生成 6 位数字验证码。
5. 通过 QQ SMTP 发送邮件。
6. 邮件发送成功后，才把验证码和生成时间保存到内存。
7. 返回统一成功响应。

邮件发送失败时不会保存验证码，用户需要重新发送。

### 8.3 前端提交注册

用户填写昵称、密码和邮箱验证码后，前端调用：

```http
POST /api/v1/auth/register
```

请求体示例：

```json
{
  "email": "user@example.com",
  "emailCode": "123456",
  "nickName": "user001",
  "password": "123456"
}
```

### 8.4 后端完成注册

后端注册处理顺序如下：

```text
请求参数校验
    ↓
校验邮箱验证码
    ↓
验证码正确后立即删除
    ↓
检查邮箱是否重复
    ↓
检查昵称是否重复
    ↓
BCrypt 加密密码
    ↓
保存用户到 MySQL
    ↓
返回用户 ID
```

任何一步失败都会终止注册，不会保存用户。

## 10. 测试范围

当前测试包括：

- `EmailCodeServiceTest`：验证码生成、发送、限流、错误校验和一次性使用。
- `AuthControllerRegressionTest`：发送接口和注册接口的调用关系。

- `RegisterRequestValidationTest`：注册请求参数校验。

这些测试使用 Mock 邮件发送器，不会真实连接 QQ SMTP，也不会发送真实邮件。真实 SMTP 的账号、授权码、网络连接和邮件投递仍需要手动验证。

## 11. 常见错误

### `Illegal address`

通常表示发件人配置为空或格式不合法。检查 `MAIL_USERNAME`，并确认后端已经重启。

### `535 Authentication failed`

通常表示 QQ 邮箱授权码错误、已失效，或误用了 QQ 登录密码。请重新生成授权码。

### 前端显示“验证码发送失败”

先查看后端控制台的异常信息。前端只显示统一错误提示，具体原因通常来自后端 SMTP 异常。

### 重启后验证码失效

这是当前内存存储的预期行为。生产环境应改用 Redis 保存验证码和过期时间。

## 12. 内存存储方案的不足

当前验证码使用 Java 进程内的 `ConcurrentHashMap` 保存，只适合开发和单机测试。

主要问题：

- 后端重启或发布后，所有未使用验证码都会丢失。
- 多实例部署时，不同实例之间不会共享验证码。
- 发送验证码和注册请求如果落到不同实例，可能校验失败。
- 如果过期记录没有及时清理，Map 会持续增长并增加内存压力。
- 服务崩溃后无法恢复验证码和限流状态。
- 无法方便地实现跨实例的邮箱限流和 IP 限流。
- 容器扩容、缩容或滚动发布时，验证码状态不稳定。
- 不利于统一监控发送次数、错误次数和风控数据。

因此，内存方案的边界是：

```text
单机开发和测试：可以使用
生产环境和集群部署：不建议使用
```

## 13. Redis 方案

生产环境应使用 Redis 保存验证码、过期时间和限流状态，使所有后端实例共享同一份数据。

推荐的数据结构：

```text
验证码：email:code:{邮箱}
错误次数：email:code:fail:{邮箱}
发送限流：email:send:limit:{邮箱}
IP 限流：email:send:ip:{IP}
```

验证码示例：

```text
KEY：email:code:user@example.com
VALUE：123456
TTL：300 秒
```

发送验证码时：

1. 统一邮箱格式。
2. 检查邮箱和 IP 是否处于限流状态。
3. 使用安全随机数生成验证码。
4. 通过 Redis 写入验证码，并设置 5 分钟 TTL。
5. 发送邮件。
6. 设置 60 秒重发限制。

校验验证码时：

1. 根据邮箱读取 Redis 中的验证码。
2. 检查验证码是否存在以及是否匹配。
3. 错误时增加错误次数，超过阈值后暂时锁定。
4. 正确时使用 Redis 删除验证码，保证只能使用一次。

Redis 的优势：

- 验证码自动过期，不需要手动清理 Map。
- 多个后端实例可以共享验证码。
- 服务重启不会影响尚未过期的数据。
- 可以使用原子操作实现限流和防重复发送。
- 支持更完整的风控、统计和监控。

## 14. Redis 迁移注意事项

迁移到 Redis 后仍需注意：

- Redis 需要配置密码、网络访问控制和持久化策略。
- 验证码不应明文打印到日志。
- 验证码校验应限制错误次数，防止暴力猜测。
- Redis 不可用时，应明确返回服务暂不可用，不能静默绕过验证。
- Redis Key 中的邮箱建议进行规范化，必要时进行脱敏处理。
- 压测时应观察 Redis 命中率、内存、连接数和命令耗时。
